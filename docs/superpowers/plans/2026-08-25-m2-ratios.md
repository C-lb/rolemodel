# M2 — Ratios and Interpretation — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** From the canonical statements M1 produces, compute 25 built-in ratios across five families with per-period trends, let the user build custom ratios by dragging line-item chips into a safe expression, and attach both authored definitional text and an on-demand generated read of what the numbers did.

**Architecture:** Everything numeric lands in `src/model/ratios/`, which stays pure: no React, no database, no I/O, covered by the existing purity guard. `src/extract/` gains an interpretation client that mirrors the extraction client's seam. `src/server/` gains persistence for custom ratios, cached interpretations, and the averaging mode. `src/ui/` gains ratio cards, a sparkline, and the builder drawer, and holds no financial logic.

**Spec:** `docs/superpowers/specs/2026-08-25-m2-ratios-design.md`
**Parent spec:** `docs/superpowers/specs/2026-08-25-financial-modelling-webapp-design.md`

## Global Constraints

Everything in the M1 plan's Global Constraints still applies. Repeated here because they are the ones that bite:

- TypeScript `strict: true`, no `any` in committed code.
- Claude model ID is exactly `claude-opus-5`. Never append a date suffix.
- Every Claude request sets `thinking: { type: "adaptive" }`. Never send `budget_tokens`.
- Structured output uses `client.messages.parse()` with `zodOutputFormat(...)` in `output_config.format`. `response.parsed_output` can be `null`; always guard.
- `src/model/` imports nothing from `app/`, `db/`, `ingest/`, or `extract/`. Enforced by `src/model/purity.test.ts`.
- All monetary and ratio comparisons use `src/model/tolerance.ts`, never `===`.
- Migrations are idempotent DDL appended to the `DDL` array in `src/db/client.ts`. Adding a column to an existing table is a guarded `ALTER TABLE`, because `CREATE TABLE IF NOT EXISTS` will not add it to a database that already exists.
- TDD throughout: failing test first, then implementation. Commit after every task with a conventional prefix.
- No new runtime dependencies. The sparkline is hand-written SVG; the expression parser is hand-written recursive descent.

M2-specific:

- A ratio never evaluates to `NaN` or `Infinity`. Every non-numeric outcome is a named state.
- Sign normalisation is a fixed exported list of canonical keys, never a heuristic on the sign of a value.
- The interpretation payload contains computed numbers, labels, and definitional text only. Never document text, raw labels, or provenance strings.

### Task 2: Safe expression parser and evaluator

**Files:**
- Create: `src/model/ratios/expression.ts`
- Test: `src/model/ratios/expression.test.ts`

**Interfaces:**
- Consumes: nothing
- Produces:
  - `type Node = { kind: "number"; value: number } | { kind: "ident"; name: string } | { kind: "unary"; op: "-"; operand: Node } | { kind: "binary"; op: "+" | "-" | "*" | "/"; left: Node; right: Node }`
  - `interface ParseError { message: string; offset: number }`
  - `type ParseResult = { ok: true; node: Node } | { ok: false; error: ParseError }`
  - `function parseExpression(input: string): ParseResult`
  - `function identifiers(node: Node): string[]` — deduplicated, in source order
  - `type Resolve = (name: string) => number | undefined`
  - `type EvalResult = { kind: "ok"; value: number } | { kind: "unavailable"; missing: string[] } | { kind: "undefined_denominator"; reason: "zero" | "negative" }`
  - `function evaluate(node: Node, resolve: Resolve, opts?: { positiveDenominator?: boolean }): EvalResult`

- [x] **Step 1: Write the failing parser test**

Valid: `a / b`, `(a + b) / c`, `-a + 2.5 * b`, `a - b - c` (left associative), `a / b / c` (left associative), `2 * (a + (b - c))`. Precedence: `a + b * c` parses as `a + (b * c)`.

Rejected with the right offset: `a +`, `(a`, `a )`, ``, `   `, `a $ b`, `a / 0`, `a ** b`, `eval(a)`, `a; drop table`.

`identifiers` returns `["a","b"]` for `a / (b + a)`.

- [x] **Step 2: Write the tokeniser and recursive-descent parser**

Grammar exactly as spec §5. Tokens: number (with optional decimal part), identifier (`[a-z][a-z0-9_]*`), the four operators, parentheses. Any other character is an error carrying its offset. No `eval`, no `new Function`, no regex-driven evaluation.

Reject literal division by zero at parse time, since it can never be anything but an error.

- [x] **Step 3: Write the failing evaluator test**

`ok` for a resolvable expression. `unavailable` naming every missing identifier, not just the first, because a card that says "missing inventory" then says "missing cost of revenue" after a fix wastes a round trip. `undefined_denominator` with `reason: "zero"` when a denominator resolves to zero within tolerance; `reason: "negative"` only when `positiveDenominator` is set. Division nested inside a larger expression propagates the same states. No result is ever `NaN` or `Infinity`; assert that explicitly with `Number.isFinite`.

- [x] **Step 4: Implement `evaluate`**

Depth-first, short-circuiting on the first non-`ok` state, collecting all missing identifiers before returning.

- [x] **Step 5: Verify**

Tests green, typecheck and lint clean. Commit: `feat: safe expression parser and evaluator for ratios`

### Task 3: The ratio computation engine

**Files:**
- Create: `src/model/ratios/compute.ts`
- Test: `src/model/ratios/compute.test.ts`, `src/model/ratios/fixtures.ts`

**Interfaces:**
- Consumes: `WorkspaceView`, `Cell` from `@/model/workspace`; `sortPeriodsMostRecentFirst`, `isImmediatePredecessor` from `@/model/periods`; Tasks 1 and 2
- Produces:
  - `type AveragingMode = "average" | "ending"`
  - `interface RatioComponent { name: string; storedValue: number | undefined; usedValue: number | undefined; averaged: boolean; magnitudeApplied: boolean; periodKey: string }`
  - `interface RatioNote { code: "averaging_fallback" | "quarterly_annualised" | "mixed_period_types" | "low_confidence" | "contains_override"; detail: string }`
  - `interface RatioPeriodResult { periodKey: string; state: "ok" | "unavailable" | "undefined_denominator"; value: number | undefined; missing: string[]; denominatorReason: "zero" | "negative" | undefined; components: RatioComponent[]; dayMultiplier: number | undefined; confidence: number | undefined; notes: RatioNote[] }`
  - `interface RatioResult { key: string; label: string; family: RatioFamily; unit: RatioUnit; direction: RatioDirection; isCustom: boolean; periods: RatioPeriodResult[] }`
  - `interface ComputeInput { workspace: WorkspaceView; mode: AveragingMode; custom: { key: string; label: string; expression: string; note: string | null }[] }`
  - `function computeRatios(input: ComputeInput): RatioResult[]`
  - `function dupont(results: RatioResult[]): DupontResult` — the three components plus the reconciliation check per spec §3

- [x] **Step 1: Build the fixture**

`fixtures.ts` exports a three-period (`FY2022`, `FY2023`, `FY2024`) `WorkspaceInput` with round numbers chosen so every one of the 25 ratios has a hand-computable answer, plus variants: a one-period workspace (averaging has no prior), a workspace with negative equity, one with zero interest expense, one missing the cash-flow statement entirely, and one mixing `FY2024` with `Q1-2025`.

Hand-compute the expected values and write them as literals in the test. Do not compute expectations with the code under test.

- [x] **Step 2: Write the failing semantics tests**

One test per rule in spec §4:

- Flow-over-stock ratios average in `average` mode when the prior period exists (`roa` on `FY2024` uses the mean of `FY2023` and `FY2024` total assets).
- The same ratios use the ending balance in `ending` mode.
- Stock-over-stock ratios (`current_ratio`, `debt_to_equity`) never average, in either mode.
- The earliest period falls back to ending balance and emits an `averaging_fallback` note.
- `days` is 365 for `FY` and 91.25 for `Q`, and a quarterly days ratio emits `quarterly_annualised`.
- Each `MAGNITUDE_KEYS` member is read as a magnitude, and the component records `magnitudeApplied: true` alongside the stored negative value.
- Missing input yields `unavailable` naming every missing key.
- Zero denominator yields `undefined_denominator` with `reason: "zero"`; negative equity yields `reason: "negative"` for `roe` but a plain number for `equity_multiplier`, which does not set `denominatorMustBePositive`.
- Confidence is the minimum across components; a component override sets `contains_override`; a component below 0.6 sets `low_confidence`.
- Periods come back most recent first.
- A mixed `FY`/`Q` workspace flags days-based and turnover ratios with `mixed_period_types`.
- Custom ratios evaluate under identical rules, including averaging and magnitude handling.
- A custom ratio referencing another custom ratio resolves; a cycle is reported rather than looping.
- DuPont reconciles to `roe` within tolerance on the fixture, and reports which component is missing when one is `unavailable`.

- [x] **Step 3: Implement `computeRatios`**

Resolution order per period: identifier is a taxonomy key (apply magnitude, then averaging per §4.1), otherwise a built-in ratio key, otherwise a custom ratio key, otherwise missing. Ratio-to-ratio references are topologically sorted once per compute call with cycle detection.

The flow-over-stock test is a property of the expression, not of the ratio: an expression averages its balance-sheet identifiers when it also references at least one income or cash-flow identifier. Derive that from `TAXONOMY[].statement`, so a custom ratio gets it for free.

- [x] **Step 4: Verify**

All tests green, purity test still green, typecheck and lint clean. Commit: `feat: ratio computation engine with averaging, magnitudes and named failure states`

## Outcome

All eight tasks landed, TDD throughout, one commit each. `npm test` (409), `tsc --noEmit`,
`eslint`, `next build` and `playwright test` (4) are green.

Deviations from the plan as written, and why:

- **`dayScaled` on `RatioDef`.** The spec wrote `* days` into the DSO, DIO and DPO formulas,
  but `days` is not a line item the parser can resolve. The multiplier is a flag the engine
  applies instead, deliberately false on the cash conversion cycle, which sums three figures
  already in days.
- **A fourth evaluator state, `not_a_number`.** Guarding division still leaves arithmetic
  overflow, and the three planned states had nowhere honest to put it. The engine maps it to
  `unavailable`, so the card contract is unchanged.
- **`ratiosAgree` rather than `closeEnough` for the DuPont check.** The shared money tolerance
  carries an absolute floor of one currency unit, which would call 0.14 and 0.30 the same
  number. Ratios compare relatively.
- **A separate `WorkspaceRatios.test.tsx`** instead of extending the M1 screen test. The two
  files test different surfaces and neither needs the other's fixtures.
- **The Playwright harness was built here**, since M1 left none: `playwright.config.ts`, a
  seeded throwaway database under `data-e2e/`, and `npm run test:e2e`.

What the browser pass caught that jsdom could not: dnd-kit claimed the pointer on press in the
ratio builder, so pressing a chip never fired its click. The keyboard-accessible path the spec
requires was broken in every real browser while its unit test passed. The sensor now needs four
pixels of travel before a drag starts.

## Definition of done

- 25 built-in ratios compute correctly against a hand-verified fixture in both averaging modes.
- Every rule in spec §4 has a test that fails when the rule is removed.
- Custom ratios are drag-built, keyboard-buildable, validated at save time, and cycle-safe.
- Every ratio card shows its components and links each one back to M1 provenance.
- Interpretation is on demand, cached, grounded only in computed numbers, and degrades to a message without ever hiding the numbers.
- Every ratio and every new control has a tooltip, enforced by the registry test.
- `npm test`, `tsc --noEmit`, `lint`, and `build` are clean, and the M1 suite still passes.
