# M3 — Forecast, Scenarios, Sensitivity — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** From the historical statements M1 extracted, project a linked three-statement forecast driven by seventeen explicit drivers, hold independent driver sets in arbitrary scenarios seeded with Base, Bull and Bear, and re-run the whole forecast across a two-variable sensitivity grid.

**Architecture:** All arithmetic lands in `src/model/forecast/`, which stays pure and is covered by the existing purity guard. `src/model/periods.ts` gains annual extension so one module still owns what a period key is. `src/model/taxonomy.ts` gains `revolver` and `src/model/ratios/library.ts` folds it into the debt expressions. `src/server/` gains scenario and driver persistence plus a forecast assembler. `src/ui/` gains the scenario bar, driver grid, forecast statements and sensitivity grid, and holds no financial logic.

**Spec:** `docs/superpowers/specs/2026-08-26-m3-forecast-design.md`
**Parent spec:** `docs/superpowers/specs/2026-08-25-financial-modelling-webapp-design.md`

## Global Constraints

Everything in the M1 and M2 plans' Global Constraints still applies. Repeated here because they are the ones that bite:

- TypeScript `strict: true`, no `any` in committed code.
- Claude model ID is exactly `claude-opus-5`. Never append a date suffix.
- `src/model/` imports nothing from `app/`, `db/`, `ingest/`, or `extract/`. Enforced by `src/model/purity.test.ts`. Add `src/model/forecast/` to whatever that guard globs if it is not already covered.
- All monetary comparisons use `closeEnough` from `src/model/tolerance.ts`, never `===`.
- Migrations are idempotent DDL appended to the `DDL` array in `src/db/client.ts`. Adding a column to an existing table is a guarded `ALTER TABLE`, because `CREATE TABLE IF NOT EXISTS` will not add it to a database that already exists.
- TDD throughout: failing test first, then implementation. Commit after every task with a conventional prefix.
- No new runtime dependencies.
- Every new user-facing control gets a tooltip registry entry; the registry completeness test already fails without one.

M3-specific:

- A forecast cell is never `NaN` or `Infinity`. Every failure is a named finding and the columns are withheld rather than half-drawn.
- Signs follow the extraction convention already in the codebase: costs and outflows are negative. The forecast must not invent a second convention.
- Forecast cells are computed, never overridable. Direct overrides on computed cells would break the articulation invariant everything else rests on.
- The articulation invariant is mutation-tested. A guard that has never been seen to go red cannot be trusted.

### Task 2: Shared model surface — revolver, finding codes, and the workspace forecast layer

Four edits to files M1 and M2 own. They are grouped because they carry one risk: changing a
shared model file and silently moving an M1 finding or an M2 historical ratio. The tests that
prove they did not are the point of this task.

**Files:**
- Modify: `src/model/taxonomy.ts`, `src/model/ratios/library.ts`, `src/model/validate.ts`, `src/model/workspace.ts`, `src/ui/Banner.tsx`
- Test: `src/model/taxonomy.test.ts`, `src/model/ratios/library.test.ts`, `src/model/validate.test.ts`, `src/model/workspace.test.ts`, `src/ui/Banner.test.tsx`

**Interfaces:**
- Produces:
  - taxonomy key `revolver` on `balance`, `parentKey: "total_current_liabilities"`, `order: 445`, `isSubtotal: false`
  - `FINDING_CODES` gains `forecast_not_annual`, `forecast_missing_base`, `forecast_articulation_broken`, `forecast_revolver_drawn`, `forecast_equity_negative`, `forecast_driver_default`
  - `FindingSeverity` gains `"info"`
  - `Cell["source"]` gains `"forecast"`
  - `WorkspaceInput` gains `forecast?: { periods: string[]; valueAt: ValueLookup }`

Why these four and not the engine's own module: `FindingCode` is a closed union, `computeRatios`
reads a `WorkspaceView` and nothing else, and `Cell["source"]` has no honest member for a
computed cell. Spec §7's promise of ratios over forecast periods is only reachable through the
workspace seam M1 already built. Forking a parallel finding type or a second ratio entry point
would buy nothing and fork two shapes the whole UI consumes.

- [ ] **Step 1: Write the failing taxonomy and ratio tests**

Taxonomy: `revolver` exists, sits between `short_term_debt` and `other_current_liabilities` by
`order`, and is a component of `total_current_liabilities`.

Ratio library: every expression that sums `short_term_debt` and `long_term_debt` also sums
`revolver`. Assert this structurally — parse each expression with `parseExpression`, collect
`identifiers`, and require that any expression containing both debt keys also contains
`revolver`. A hand-listed set of ratio keys will rot the first time a ratio is added.

- [ ] **Step 2: Write the failing regression test**

The existing M1 fixtures produce exactly the same findings after the taxonomy addition as
before, and the existing M2 fixtures produce exactly the same historical ratio values. This is
the regression that matters; a new component of a subtotal is precisely the kind of change that
silently starts failing a subtotal check.

- [ ] **Step 3: Write the failing workspace forecast-layer test**

With no `forecast` input, `buildWorkspace` behaves exactly as before — assert against the
existing M1 workspace fixtures, unchanged. With a `forecast` layer: `periods` includes the
forecast keys; a forecast cell has `source: "forecast"`, the layer's value, and `undefined` for
`extractedValue`, `confidence` and `provenance`; an override never shadows a forecast cell,
because forecast cells are not overridable; a historical cell is unaffected by the presence of
the layer.

Then the payoff test: `computeRatios` over a workspace carrying a forecast layer produces ratio
values for forecast periods, and the historical values in the same result are identical to those
from the same workspace without the layer.

- [ ] **Step 4: Write the failing finding and Banner tests**

`FINDING_CODES` contains the six new codes. A finding with `severity: "info"` renders in
`Banner` with its own tone, is not styled as a failure, and does not claim the blocking
treatment. The existing blocking and warning renders are unchanged.

- [ ] **Step 5: Implement**

Add the taxonomy entry with a `definition` explaining that it is the forecast's funding plug and
is absent in extracted historicals.

Update the debt expressions in `library.ts`. Historical values are unchanged because `revolver`
is always absent there; say so in a comment so the next reader does not think this moved M2's
numbers.

In `workspace.ts`, resolve a cell against the forecast layer only when its period is in the
layer's period list. Do not merge the two period lists by concatenation and hope the ordering
holds — sort through `sortPeriodsMostRecentFirst` so there is still one ordering rule.

- [ ] **Step 6: Verify**

Full `npm test` green, not just the touched files. This task can break M1 and M2 and the point of
it is proving it did not. `tsc`, `lint`. Commit: `feat: shared model surface for the forecast layer`

### Task 4: The forecast engine

The big one. Do not start it until Tasks 1 to 3 are committed and green.

**Files:**
- Create: `src/model/forecast/engine.ts`
- Test: `src/model/forecast/engine.test.ts`

**Interfaces:**
- Consumes: `TAXONOMY`, `closeEnough`, `Finding` from `@/model/validate`, `DRIVER_KEYS`
- Produces:
  - `interface ForecastInput { historicalPeriods: string[]; forecastPeriods: string[]; valueAt(key: string, period: string): number | undefined; driverAt(key: string, period: string): number | undefined; driverBasisAt?(key: string, period: string): DriverBasis | undefined }`
  - `interface PlugDetail { periodKey: string; cashBeforePlug: number; drawn: number; repaid: number; revolverBalance: number }`
  - `interface ForecastCell { canonicalKey: string; periodKey: string; value: number; formula: string; inputs: { label: string; value: number }[] }`
  - `interface ForecastResult { ok: boolean; cells: ForecastCell[]; plugs: PlugDetail[]; findings: Finding[]; valueAt(key: string, period: string): number | undefined }`
  - `function runForecast(input: ForecastInput): ForecastResult`

`formula` and `inputs` on each cell are what the forecast's provenance panel renders in Task 8. Populate them as the value is computed, not by re-deriving them afterwards.

- [ ] **Step 1: Write the failing engine test against a hand-verified fixture**

Extend `fixtures.ts` with the expected forecast for two periods, computed by hand from spec §5 and written as literals. Two periods, because the second is the only one that exercises a forecast period opening from another forecast period rather than from history.

Assert, one test each:
- Every income-statement line matches its literal.
- Every cash-flow line matches its literal.
- Every balance-sheet line matches its literal.
- Signs: `cost_of_revenue`, `interest_expense`, `income_tax_expense`, `capital_expenditures` and `dividends_paid` each have the same sign in the forecast as in the last historical period.
- Subtotals equal the sum of their taxonomy components rather than being carried forward.
- Held-flat items equal their opening balance; held-at-zero items are zero.
- `retained_earnings` moves by exactly `net_income + dividends_paid`.
- `property_plant_equipment` moves by exactly `|capex| - depreciation_amortisation`.
- A loss period pays zero tax rather than a credit.
- `depreciation_amortisation` reads opening PP&E, not closing.
- `interest_expense` reads opening debt, not closing, and includes the opening revolver.

- [ ] **Step 2: Write the failing plug test**

Four cases from spec §11: a surplus period, a deficit period that draws, a period that draws followed by one that repays in full, and a period whose surplus is smaller than the outstanding revolver so it repays partially and cash stays at the floor. Each asserts the `PlugDetail`, the revolver balance, and `cash_from_financing` including the revolver movement.

- [ ] **Step 3: Write the failing articulation test**

For every forecast period, `total_assets` is `closeEnough` to `total_liabilities + total_equity`, and `cash[P] + net_change_in_cash` is `closeEnough` to the plugged cash.

- [ ] **Step 4: Write the failing findings test**

One test per code in spec §5.6. `forecast_not_annual` when the last historical is a quarter. `forecast_missing_base` when a needed opening balance is absent, asserting which key it names. `forecast_revolver_drawn` as a warning that does not set `ok: false`. `forecast_equity_negative`. `forecast_driver_default` when `driverBasisAt` reports at least one `default` basis, and absent when every driver is derived or when no `driverBasisAt` is supplied. Blocking findings set `ok: false` and return no cells at all, rather than a partial set.

- [ ] **Step 5: Implement the engine**

Evaluate periods in order. Within a period follow spec §5 top to bottom: income statement, then working capital and the cash-flow statement, then the plug, then the balance sheet. Read every `[P]` reference through one helper so "opening balance" cannot accidentally become "closing balance" in one line out of forty.

- [ ] **Step 6: Mutation-test the articulation guard**

Break the engine deliberately, one mutation at a time, and confirm the articulation test goes red for each. At minimum: drop `change_in_working_capital` from `cash_from_operations`; drop `stock_based_compensation` from `common_stock_apic`; drop `dividends_paid` from `retained_earnings`; use closing PP&E for depreciation. Revert each mutation immediately.

Record the result in the task's commit message. If any mutation leaves the suite green, the guard is decorative and the test is wrong, not the mutation.

- [ ] **Step 7: Verify**

Full `npm test` green, `tsc`, `lint`. Commit: `feat: acyclic three-statement forecast engine with a revolver plug`

### Task 5: Sensitivity grid

**Files:**
- Create: `src/model/forecast/sensitivity.ts`
- Test: `src/model/forecast/sensitivity.test.ts`

**Interfaces:**
- Consumes: `runForecast`, `computeRatios`
- Produces:
  - `type SensitivityOutput = { kind: "lineItem" | "ratio"; key: string; periodKey: string }`
  - `interface Axis { driverKey: string; min: number; max: number; steps: 3 | 5 | 7 }`
  - `type SensitivityCell = { state: "ok"; value: number; isBase: boolean } | { state: "failed"; reason: string; isBase: boolean }`
  - `interface SensitivityResult { rows: number[]; columns: number[]; cells: SensitivityCell[][] }`
  - `function sensitivityGrid(input: ForecastInput, rowAxis: Axis, columnAxis: Axis, output: SensitivityOutput, ratios: CustomRatioInput[], mode: AveragingMode): SensitivityResult`

A ratio output is read by building a `WorkspaceView` with the forecast layer from Task 2 and
calling `computeRatios`. There is no second ratio entry point.

- [ ] **Step 1: Write the failing test**

Grid shape matches `steps` on each axis. Axis values are evenly spaced, inclusive of both endpoints, and a `steps: 3` axis from 0 to 0.1 gives exactly `[0, 0.05, 0.1]`. Both axis drivers are applied to every forecast period, not only the first: assert by choosing a `revenue_growth` axis and checking the final-period revenue compounds.

A known analytic result: with every driver but `revenue_growth` fixed, revenue in forecast period two is `revenue[last] * (1+g)^2` for each `g` on the axis.

A ratio output whose denominator goes to zero reports the ratio engine's own state rather than `NaN`. A cell whose forecast returns a blocking finding is `state: "failed"` with the finding code as `reason`. The base-case flag is set only on a cell whose axis values both equal the scenario's current driver values, and is absent from every cell when neither axis passes through them.

- [ ] **Step 2: Implement**

Each cell wraps the input's `driverAt` in a function that returns the axis value for the two axis keys in every forecast period and delegates otherwise. Wrap; never mutate a shared lookup. Cap the work at 49 evaluations by typing `steps` as the literal union; there is no runtime clamp to test because the type makes the invalid value unrepresentable.

- [ ] **Step 3: Verify**

`npm test -- src/model/forecast` green, `tsc`, `lint`. Commit: `feat: two-variable sensitivity grid over the forecast`

## Definition of done

- A forecastable workspace produces five annual forecast periods across three seeded scenarios, driven entirely by editable drivers.
- The forecast balance sheet balances in every period, and the test proving it has been seen to go red under four separate deliberate mutations.
- Every forecast cell can explain itself: its formula, the drivers it consumed, and the opening balances it read.
- Forecast cells cannot be overridden, and the reason is visible to the user rather than a silent absence.
- A two-variable sensitivity grid runs over any line item or ratio at any forecast period, and its failure cells name their reason.
- The `revolver` addition changed no M1 finding and no M2 historical ratio, proved by the existing suites.
- Every new control has a tooltip, enforced by the registry test.
- `npm test`, `tsc --noEmit`, `lint`, `build` and `test:e2e` are clean, and the M1 and M2 suites still pass.
